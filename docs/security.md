# The Judge v4.0 Security Policy & Security Model

## Core Philosophy

The Judge operates on a fundamental security principle:

> **The target code under verification is UNTRUSTED.**
> **The Judge verification engine is a TRUSTED VERIFIER.**

Target code may be generated by AI models, third-party contributors, or hostile adversaries. The Judge treats target code as actively untrusted software attempting to discover evaluation criteria, bypass sandboxes, modify evidence, or trick the verifier into returning `PASS`.

---

## Security Invariants

### 1. Zero Sandbox Leakage (0.0% Leakage Guarantee)

All execution of target code and synthesized test suites occurs inside isolated subprocess sandboxes with anonymous paths and sanitized environment variables.
- Subprocesses run with restricted environment variables.
- Sensitive environment variables (e.g. `DEBUG`, `SECRET_KEY`, `AWS_ACCESS_KEY_ID`, `GIT_CONFIG`) are stripped before sandbox execution.

### 2. Challenge Integrity & Anti-Tampering

- Challenge tests are generated dynamically with random, non-predictable function names.
- File integrity checks track SHA-256 hashes of test challenge scripts. If target code modifies or deletes a challenge file during execution, `Hard Gate 7 (COLLECTION TAMPERING DETECTED)` immediately triggers `FAIL`.

### 3. Synthesis Evasion Policy

The Judge refuses to grant `PASS` based only on agent-authored unit tests or visible workspace tests. At least one independent behavioral property challenge must pass before `PASS` can be awarded.

### 4. Multi-Round Regression Protection

When run in a multi-round repair loop, `Hard Gate 6 (REGRESSION DETECTED)` compares previous evidence snapshots with current evidence snapshots. Any regression in previously verified behaviors blocks the release.

---

## Reporting Vulnerabilities

If you discover a sandbox escape vector, property synthesis evasion technique, or verifier denial vulnerability, please report it via the security issue tracking protocol. All security regressions will be encoded as permanent regression tests in `tests/`.
